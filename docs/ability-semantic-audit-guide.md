# カード文と実装の処理要素を照合する監査（案①）

## 目的と判定の意味

「テンプレートに分類できた」を「カード文通りに動く」と取り違えないための開発用監査。
未対応だけでなく、分類済みカードのコスト・移動先・枚数・条件・後続処理の取りこぼしを探す。
対象は `data/cards.json` の全カード・全レアリティ。メンバー、ライブ、常時、自動も含む。
過去にコードでIDを参照したカードや修正済みカードを除外しない。

| 状態 | 意味 | 次の作業 |
|---|---|---|
| unimplemented | 分類エラー・手動・未分類・none等 | 本文と分類器を確認して実装する |
| suspect | 要求と分類フィールドの不一致、または処理契約で対応を確認できない効果がある | 不具合の疑い。実ハンドラを読み、再現テストで確認する |
| needs_review | 契約未登録、未知の文言、枚数未確認、後続処理、静的に見つからないハンドラ等 | 不具合とは限らない。契約と処理を監修する |
| checked_known_rules | 今回抽出できた既知ルールの要求は一致 | 動作保証・全要件の監修完了ではない |

**指摘数はカード数ではなく能力セグメント数。レアリティ違いは別々に数える。**
Markdownでは未対応と不一致の疑いを詳しく表示し、要確認をテンプレート別に集計する。
JSONの `records` には全セグメントの原文、抽出要求、分類結果、指摘と根拠を保存する。

## サイトとの関係・普段の使い方

案①は開発者向けの監査プログラム。ラブカラボの画面に検査ボタンを追加したものではなく、サイトを開くだけで常時監視が動くものでもない。カード文と分類結果・実行ハンドラ・処理契約を読み、欠落の疑いをファイルに出す。
検出だけではカード効果は変わらない。今回の未対応修正は、この監査とは別にゲームの分類器・実処理・発動イベントも変更している。

1. Macのターミナルで次を実行する。

```bash
cd /Users/kaneko_kai/projects/ll-ocg-tools
npm run audit:abilities
```

2. このプロジェクトの `docs/ability-semantic-audit.md` をCursorなどで開く。未対応・不一致の疑いと根拠を確認できる。全セグメントの詳細は同名JSONにある。
3. 指摘を修正したら `npm run test:abilities` で全体検証する。今回追加した能力だけなら `npm run test:pending-abilities`。
4. 全件監査を実行すると `docs/HANDOFF.md` の集計も更新され、Cursorと共有できる。個別カード監査は全件結果を上書きしない。

`daily-card-update.sh` でカードデータを更新する際と、全体検証を実行する際にも監査が動く。新たなOS定期ジョブは登録していない。監査は自動修正を行わず、未登録契約や未知の文言は要確認として残す。

## 実行

```bash
# レポートを生成し、HANDOFFの管理ブロックを更新する。指摘があっても終了0。
npm run audit:abilities

# 未対応・不一致の疑いがある場合は終了1。
npm run audit:abilities:check

# 要確認も残っていれば終了1。
npm run audit:abilities:strict

# 欠落を意図的に注入する回帰検証など37ケース。
npm run test:ability-audit

# 単一カード。全件結果とHANDOFFを上書きせず scoped.json / scoped.md に出力。
node scripts/audit-ability-semantics.mjs --card 'PL!-pb2-000-R'

# 書き込まず機械可読JSONだけ出力。--cardは複数指定できる。
node scripts/audit-ability-semantics.mjs --card 'PL!S-cl1-006-CL' --json

# 読み取りだけで集計する。
node scripts/audit-ability-semantics.mjs --no-write
```

- `--out-dir PATH`: 別フォルダへ出力。この場合もHANDOFFは変更しない。
- 終了0: コマンドが完了した。報告モードの0は「指摘0件」ではない。
- 終了1: `--check` / `--strict` の基準に該当する指摘がある。
- 終了2: 引数・契約ファイル・出力・引き継ぎ更新など監査自体の実行失敗。
- エラー時は前のレポートを最新として扱わない。`generated_at` と `input_sha256` で生成時刻と主要入力を確認する。

## 構成

| ファイル | 役割 |
|---|---|
| scripts/lib/ability-semantic-audit.mjs | カード文からの要求抽出・分類結果との照合・HANDOFFの安全な部分更新 |
| data/ability-semantic-contracts.json | 人が確認して保守するテンプレート別の処理契約 |
| scripts/audit-ability-semantics.mjs | CLI、実ハンドラの存在確認、全件レポート出力 |
| scripts/verify-ability-semantics.mjs | 欠落注入・境界値・CLI・日次実行・引き継ぎ保護の回帰検証 |
| docs/ability-semantic-audit.md / .json | 最新の全件監査結果 |
| docs/HANDOFF.md | CursorとGPTの最新共有状態。全件監査は管理ブロックだけ更新 |
| docs/WORKLOG.md | 作業履歴。エージェントが各作業の終了前に追記 |

## 照合する要素

- コスト: 自身ウェイト、自身を控え室へ、手札を控え室／デッキ下へ、エネルギー支払い、任意コスト。
- 効果: ドロー、山札から控え室、山札を見る、控え室／エール公開から回収、デッキ上下へ移動、順序指定、選択カードのシャッフル、ブレード／ハート／スコア、相手ウェイト、能力無効、エール方向置換。
- 条件等: 元々のハート上限、公開ライブ枚数、センター、ターン回数、ステージの同グループ人数とグループ名、共通ハート色、バトンタッチ人数・コスト合計、成功ライブごとの同名枠、BHなし、移動枚数比例、ライブ終了まで。
- ハート付与は色・個数を照合する。処理の存在だけを示す契約では数値保証としない。
- 複数ステップは子テンプレートも確認する。ただし支払い済みの親コストを、子のフィールドで誤って合格にしない。
- 複数回の同じ処理や解釈できない後続文は要確認に残す。

## 契約の追加・修正手順

1. カード文と総合ルールを読み、対象の実ハンドラと共通支払い処理を確認する。
2. 分類結果から独立して、必要な処理・条件・数値を整理する。
3. `templates.<template>.capabilities` に、そのハンドラが実際に扱う要求だけを追加する。
4. `field` は数値等を読む分類フィールド、`flag` は必須のtrueフラグ、`notFlag` は移動先等の否定条件、`groupField` はグループ名、`value` は実装上の定数を表す。`heartGrant` は既存のハート付与フィールドの色・個数を確認する。
5. `true` は処理の存在を宣言するだけ。枚数・回数がある要求に無条件trueを設定しても合格にはならない。
6. 正常例だけでなく、その処理・コスト・条件を意図的に欠落させた検証を追加する。
7. `npm run test:ability-audit` と `npm run audit:abilities` を実行し、商品専用の検証も実施する。
8. `docs/HANDOFF.md` と `docs/WORKLOG.md` を更新する。

最初の契約は15テンプレート。全テンプレートの監修が終わったという意味ではない。
未登録契約が多い段階では `needs_review` が多く出る。これを解消するための一括true設定や「修正済みカードの除外」は禁止。

## 自動実行への組み込み

- `scripts/daily-card-update.sh`: カード取得と差分確認の後、差分0で終了する前に全件監査を実行する。
- 指摘による終了1は警告として記録する。監査自体の終了2は日次更新を止め、古い結果を最新扱いにしない。
- `scripts/verify-ability-coverage.mjs`: 冒頭で監査機構の自己検証と全件レポート生成を行う。既存指摘のせいで他の検証が一切走らなくなることを避け、ここでは報告モードを使う。
- この変更で新しいOSスケジュールは登録しない。既存の日次スケジュールが動いている環境で、その呼び出しに監査が加わる。

## 限界

この版は日本語を完全解釈する仕組みでも、JavaScriptの振る舞いを完全に証明する仕組みでもない。
照合できるのは既知の文言・数値・登録された処理契約。実行ハンドラの存在検査も文字列による静的確認で、分岐内部の正しさを保証しない。
順序、任意選択、複雑な条件の組み合わせ、効果期限、相手盤面への同期は、商品専用の回帰検証や実プレイ検証と併用する。
案②の仮想盤面生成や案③のAIレビューは別段階として追加できる。


## 2026-11-03 継続改善

- 控え室→デッキ上下への移動は、同じ文の移動元と移動先、または直後の「それらを」の指示関係を確認する。山札を見て残りを控え室へ置く文を、控え室からの回収と混同しない。
- ブレード付与は全出現箇所を抽出し、複数回なら要確認にする。
- 契約の空オブジェクト・不正なキー・型・既定値だけの指定を拒否する。存在を示すフラグだけでは数値を合格にしない。
- μ's DUOの複合バトン回収を16番目の契約として追加。旧誤分類の再現はテストへ注入し、実カードを不良のまま残すことに依存しない。
- `npm run test:abilities` は監査自己検証・レポート生成・索引更新の後、独立した検証を最後まで実行し、失敗をまとめて終了1で報告する。前提の自己検証・索引生成等が故障した場合は停止する。
- μ's DUOの動作確認は `npm run test:muse-duo-baton`。新規カード・実行ハンドラ検証と共に全体検証へ組み込んだ。


## 未対応修正後の確認（2026-11-03）

未対応32→0。`js/abilityCompletion.js` に文言に基づく分類を追加し、実ハンドラ・自動能力のイベントを接続。索引上の手動能力と常時未分類も0。
